# مهمة تطوير مشروع نِصاب

## 1. الهدف العام

تحويل المشروع من نموذج أولي يعتمد على قيم ونتائج تجريبية إلى تطبيق ديناميكي تكون فيه جميع البيانات التشغيلية والمالية قادمة من الـBackend وقاعدة البيانات أو من خدمة خارجية موثوقة.

يجب أن يكون تدفق البيانات كالتالي:

```text
Flutter UI -> FastAPI JSON API -> Services/Business Logic -> Database/External Services
            <- JSON Response <-
```

ممنوع ربط Flutter مباشرة بملف SQLite. يجب أن تتعامل الواجهة مع قاعدة البيانات حصراً من خلال FastAPI.

النصوص التعريفية الثابتة مثل عناوين الصفحات، أسماء الحقول، ووصف المزايا يمكن أن تبقى ثابتة. المقصود بإزالة البيانات الثابتة هو إزالة المبالغ والأسعار والتواريخ والحالات والنتائج التي تقع ضمن نطاق ربط قاعدة البيانات. خدمة المساعد AI وطريقة الدفع مستثناتان من إعادة التطوير، وفق القيود الموضحة لاحقاً.

## 2. الوضع الحالي للمشروع

### الواجهة

- Flutter/Dart مع Material 3 واتجاه RTL.
- التنقل باستخدام `go_router`.
- لا توجد حالياً مكتبة HTTP مثل Dio أو `http`.
- لا توجد طبقة Models/Repositories/API Client أو إدارة حالة مركزية.
- البيانات محفوظة داخل حالة كل شاشة، وتضيع عند الانتقال أو إعادة تشغيل التطبيق.
- شاشة الملخص لا تستقبل نتائج شاشة الأصول.

### الـBackend

- Python وFastAPI وSQLAlchemy.
- قاعدة البيانات الحالية SQLite في `zakat-system-main/zakat.db`.
- خدمة Groq تستخدم النموذج `llama-3.3-70b-versatile` وتتطلب `GROQ_API_KEY`.
- أسعار الذهب والفضة تأتي من `gold-api.com`، مع قيم fallback ثابتة حالياً.
- CORS مفتوح لجميع المصادر.
- المستخدم مكتوب كقيمة ثابتة `demo_user` في بعض العمليات.

### استخدام قاعدة البيانات حالياً

المستخدم فعلياً:

- `terms_acceptance`: حفظ الموافقة.
- `payments`: حفظ وقراءة عمليات الدفع المحاكية.

معرّف لكنه غير مستخدم فعلياً في المسارات:

- `hawl_status`.
- `zakat_calculations`.
- `zakat_assets`.

المسارات الخاصة بالحول والحساب والأصول تعيد نتائج في الذاكرة دون حفظها. مسار التحليل يعيد نتيجة ثابتة، والدفع الحالي محاكاة وليس تكاملاً حقيقياً.

## 3. الشاشات والقيم المطلوب استبدالها

### `/` — المقدمة

- الموافقة محلية فقط.
- المطلوب حفظ الموافقة عبر API بعد معرفة المستخدم الحالي.
- لا يتم الانتقال قبل نجاح الحفظ.

### `/process` — معالجة البيانات

- تستخدم `Timer` ومراحل وهمية.
- المطلوب ربطها بحالة تحليل حقيقية، أو حذف فكرة المعالجة الوهمية إذا لم توجد خدمة تحليل فعلية.
- يجب عرض loading/error/progress حقيقي قادم من Backend.

### `/hawl` — النصاب والحول

القيم الحالية الثابتة تشمل:

- الرصيد `57,250 ريال`.
- بلوغ النصاب.
- تاريخ بداية الحول.
- حالة الاستحقاق.

المطلوب جلب الرصيد وقيمة النصاب وحالة بلوغه وبداية الحول ونهايته والأيام المتبقية والاستحقاق من API.

### `/other-assets` — الأصول

القيم الحالية الثابتة تشمل:

- سعر الذهب `310` ريال/جرام.
- سعر الفضة `3.5` ريال/جرام.

المطلوب:

- جلب الأسعار من Backend.
- إنشاء وقراءة وتعديل وحذف الأصول.
- حفظ الذهب والفضة والصناديق وبقية أنواع الأصول في قاعدة البيانات.
- إعادة الإجماليات المحسوبة من Backend.
- عدم الاعتماد على State محلية بوصفها مصدر البيانات النهائي.

### `/zakat-summary` — الملخص

- يعرض حالياً مبالغ `0.00` وقيم ثابتة.
- المطلوب بناء الصفحة من استجابة Summary API موحدة.
- يجب أن تتحدث عند إضافة أصل أو تعديله أو حذفه.

### `/assistant` — المساعد

- واجهة Flutter تعيد الرد نفسه لكل سؤال.
- لا توجد حالياً معلومات أو متطلبات كافية لتغيير المساعد.
- يجب الإبقاء على واجهة المساعد وخدمة AI والنموذج والـprompt والمسارات كما هي.
- لا تنفذ تكاملاً جديداً مع مزود AI ولا تغيّر سلوك الردود الحالية.
- يسمح بتعديل المساعد فقط إذا كان التعديل ضرورياً لربطه بقاعدة البيانات، وبعد تحديد البيانات المطلوب حفظها أو قراءتها بوضوح.
- لا تُنشئ جدول محادثات ولا تحفظ الأسئلة أو الإجابات دون طلب وموافقة صريحة من العميل.

### `/payment-method` — الدفع

- المبلغ والانتقال محليان، ولا توجد عملية دفع حقيقية.
- لا توجد خدمة دفع خارجية حالياً، وهي خارج نطاق المهمة.
- يجب الإبقاء على طريقة الدفع والواجهة والتدفق الحالي كما هي.
- يسمح بالتعديل فقط فيما يتعلق بحفظ أو قراءة سجل الدفع من قاعدة البيانات وربطه بالمستخدم وجلسة الزكاة.
- لا تضف بوابة دفع أو Webhook أو SDK دفع أو اتصالاً بمنصة خارجية.

### `/payment-success` — نتيجة الدفع

- المبالغ والتاريخ ورقم العملية وحالة النجاح ثابتة.
- يسمح باستبدال بيانات العرض ببيانات سجل الدفع المحفوظ في قاعدة البيانات فقط.
- لا تغيّر معنى نجاح العملية الحالي ولا تضف تحققاً من بوابة خارجية.
- يجب توثيق أن الدفع محاكاة داخلية وليس إثباتاً على دفع مالي حقيقي.

يجب الاستمرار باستخدام SQLite الحالية في هذه المهمة. لا تنقل المشروع إلى PostgreSQL أو أي قاعدة بيانات أخرى ما لم يطلب العميل ذلك صراحةً في مهمة مستقلة لاحقاً.

## 5. المصادقة وهوية المستخدم

- يجب تنفيذ المصادقة محلياً داخل FastAPI وقاعدة SQLite الحالية. يمنع استخدام Firebase أو Supabase Auth أو أي مزود مصادقة خارجي.
- طريقة الدخول المعتمدة لهذه المهمة هي البريد الإلكتروني وكلمة المرور.
- إزالة `demo_user` تماماً من منطق الإنتاج.
- تخزين `password_hash` فقط، وعدم تخزين كلمة المرور الأصلية أو تسجيلها في logs.
- استخدام Argon2 عبر `pwdlib[argon2]` لتجزئة كلمات المرور والتحقق منها.
- استخدام JWT access token قصير العمر وrefresh token قابل للإلغاء.
- تخزين hash للـrefresh token في جدول `refresh_tokens`، مع تاريخ انتهاء وحالة إلغاء، وعدم تخزين refresh token بصورته الأصلية.
- تدوير refresh token عند التجديد وإلغاء القديم، وإلغاء جلسة الجهاز عند تسجيل الخروج.
- حفظ مفتاح توقيع JWT ومدد الصلاحية في متغيرات البيئة، وعدم كتابتها داخل الكود.
- Flutter يرسل access token في `Authorization: Bearer ...` مع كل طلب محمي.
- Backend يتحقق من التوقيع والانتهاء ويستخرج معرف المستخدم من claim `sub`.
- لا يقبل Backend `user_id` من Flutter بوصفه دليلاً على الهوية.
- كل قراءة أو تعديل يجب أن يتحقق أن السجل يخص المستخدم الحالي.
- إضافة dependency مركزية مثل `get_current_user` وحماية جميع مسارات بيانات المستخدم بها.
- إضافة قيود uniqueness وفهارس مناسبة للبريد الإلكتروني، مع توحيد البريد قبل الحفظ والمقارنة.
- تطبيق سياسة كلمة مرور واضحة والتحقق منها في Backend.
- رسائل فشل الدخول يجب ألا تكشف هل البريد موجود أم لا.
- إضافة rate limiting لمحاولات الدخول والتسجيل والتجديد، بحسب الإمكانات المتاحة في بيئة النشر.
- في Flutter، حفظ access/refresh tokens باستخدام `flutter_secure_storage` لا SharedPreferences.
- إضافة AuthRepository وAuthState مركزيين، واستعادة الجلسة عند تشغيل التطبيق، وتجديد access token عند انتهائه، ومسح الرموز عند تسجيل الخروج.
- إضافة شاشات التسجيل وتسجيل الدخول وحالة تحميل وأخطاء واضحة، وحماية مسارات التطبيق التي تتطلب مستخدماً مسجلاً.

مسارات المصادقة المطلوبة:

```text
POST /api/auth/register
POST /api/auth/login
POST /api/auth/refresh
POST /api/auth/logout
GET  /api/auth/me
```

استعادة كلمة المرور والتحقق عبر البريد أو OTP خارج نطاق هذه المهمة لأنهما يحتاجان خدمة خارجية. لا تنفذهما قبل أن يحدد العميل مزود الإرسال وآلية التحقق.

## 6. عقد الـAPI المطلوب

استخدم Pydantic request/response schemas وأجسام JSON. يفضل استخدام مفاتيح إنجليزية مستقرة في JSON، مع إبقاء الترجمة العربية داخل Flutter.

الحد الأدنى للمسارات:

```text
POST   /api/auth/register
POST   /api/auth/login
POST   /api/auth/refresh
POST   /api/auth/logout
GET    /api/auth/me
POST   /api/terms/accept

POST   /api/zakat-sessions
GET    /api/zakat-sessions/{session_id}
GET    /api/zakat-sessions/{session_id}/summary

POST   /api/zakat-sessions/{session_id}/assets
GET    /api/zakat-sessions/{session_id}/assets
PUT    /api/zakat-sessions/{session_id}/assets/{asset_id}
DELETE /api/zakat-sessions/{session_id}/assets/{asset_id}

POST   /api/zakat-sessions/{session_id}/hawl
GET    /api/zakat-sessions/{session_id}/hawl

GET    /api/prices/live
POST   /api/ai/assistant                     # يبقى كما هو؛ خارج نطاق التعديل

POST   /api/payment/pay                      # تعديل قاعدة البيانات فقط عند الحاجة
GET    /api/payment/completed                # قراءة قاعدة البيانات فقط
```

### Summary API

يجب أن يكون Backend هو المصدر النهائي للإجماليات، وأن يعيد على الأقل:

```json
{
  "session_id": 41,
  "assets": [],
  "total_assets": 70343.75,
  "nisab_value": 30000.0,
  "reached_nisab": true,
  "hawl_completed": true,
  "total_zakat": 1758.59,
  "currency": "SAR"
}
```

لا يجب أن تحسب Flutter نتيجة نهائية مستقلة قد تختلف عن Backend.

### الأخطاء

أعد أخطاء موحدة، مثلاً:

```json
{
  "code": "INVALID_GOLD_WEIGHT",
  "message": "يجب أن يكون وزن الذهب أكبر من صفر"
}
```

تحقق في Backend من القيم والملكية والصلاحيات حتى لو تحققت Flutter منها مسبقاً.

## 7. خدمة الأسعار

- اجلب السعر من الخدمة الخارجية في Backend فقط.
- أعد العملة والمصدر ووقت آخر تحديث.
- خزّن السعر الذي استُخدم في كل حساب حتى لا يتغير الحساب التاريخي عند تغير السوق.
- استخدم cache قصير المدة لتقليل الاتصالات الخارجية.
- لا تعرض قيمة fallback على أنها سعر مباشر.
- إذا استُخدم fallback، يجب أن يحتوي الرد على `is_fallback: true` وتعرض الواجهة تنبيهاً مناسباً.

## 8. التعديلات المطلوبة في Flutter

### Dependencies

- إضافة عميل HTTP، ويفضل Dio.
- إضافة إدارة حالة مركزية، مثل Riverpod أو BLoC، باختيار واحد فقط وتطبيقه باتساق.
- يمكن استخدام `freezed` و`json_serializable` لتوليد Models إذا كان ذلك متوافقاً مع المشروع.

تحقق من الإصدارات المتوافقة مع Flutter/Dart المستخدمين قبل تعديل `pubspec.yaml`.

### البنية المقترحة

```text
lib/
  core/
    network/
      api_config.dart
      api_client.dart
      api_exception.dart
    auth/

  features/
    <feature>/
      data/
        models/
        repositories/
      presentation/
        providers/ أو bloc/
        views/
        widgets/
```

### قواعد التنفيذ

- عنوان API مركزي وقابل للتغيير عبر `--dart-define` أو إعداد بيئة.
- Android Emulator يستخدم عادة `10.0.2.2` للوصول إلى خادم الجهاز المحلي؛ لا تنشر عنواناً محلياً في إعداد الإنتاج.
- ApiClient مركزي يضيف token والمهلة ومعالجة الأخطاء.
- Models typed بدلاً من تمرير `Map<String, dynamic>` في الواجهة.
- Repository لكل مجال، ولا توضع طلبات Dio مباشرة داخل `build()`.
- حالة مركزية تحتفظ بـ`sessionId` والأصول والحول والملخص والدفع.
- كل شاشة ديناميكية تدعم loading/error/empty/data.
- لا تعرض `0.00` بوصفها نتيجة أثناء التحميل؛ استخدم مؤشر تحميل أو `--`.
- بعد إنشاء/تعديل/حذف أصل، أعد تحميل الأصول والملخص أو حدّث الحالة من رد موثوق.
- يجب استعادة الجلسة والبيانات بعد إغلاق التطبيق وإعادة فتحه.

## 9. الدفع

الدفع الحالي محاكاة داخلية ولا توجد خدمة دفع حقيقية. يجب الالتزام بالآتي:

- لا تضف أو تقترح أو تهيئ بوابة دفع خارجية ضمن هذه المهمة.
- لا تضف Webhook أو SDK دفع أو إعادة توجيه إلى منصة خارجية.
- لا تغيّر واجهة اختيار طريقة الدفع أو منطقها إلا بقدر ما يلزم لربطها بقاعدة البيانات.
- يسمح بربط سجل `payments` بالمستخدم الحالي و`zakat_session`، وحفظ الطريقة والمبلغ ورقم العملية والتاريخ وقراءة السجل للعرض.
- يجب أن يستخرج Backend المستخدم من المصادقة، لا من `demo_user` أو `user_id` يرسله Flutter.
- يجب توثيق أن السجل يمثل عملية محاكاة داخل النظام ولا يؤكد تحويلاً مالياً حقيقياً.
- أي تكامل دفع حقيقي هو مهمة مستقبلية منفصلة تحتاج موافقة العميل وبيانات مزود الدفع.

## 10. الأمان والإعدادات

- لا تلتزم بملفات `.env` أو `zakat.db` أو `.venv` أو الأسرار في Git.
- يجب أن يتضمن `.gitignore` على الأقل:

```gitignore
.env
.venv/
*.db
__pycache__/
```

- أضف `.env.example` بلا أسرار، مع أسماء المتغيرات المطلوبة فقط.
- قيّد CORS في الإنتاج.
- استخدم HTTPS في الإنتاج.
- لا تسجل tokens أو بيانات مالية حساسة في logs.
- أضف rate limiting مناسباً لمسارات المصادقة والمسارات الحساسة.

## 11. ترتيب التنفيذ الإلزامي

1. تشغيل الاختبارات الحالية وتسجيل baseline وأي أخطاء موجودة مسبقاً.
2. حماية الأسرار وتحديث `.gitignore` وإضافة `.env.example`.
3. اعتماد تصميم قاعدة البيانات والعلاقات.
4. إضافة Alembic migrations.
5. تنفيذ المصادقة المحلية عبر FastAPI وSQLite وArgon2 وJWT، ثم إزالة `demo_user`.
6. تنفيذ `zakat_sessions`.
7. تنفيذ CRUD الأصول والحول والحفظ الفعلي.
8. تنفيذ Summary API واختباره مستقلاً عبر FastAPI.
9. تحسين خدمة الأسعار والاستجابة الاحتياطية.
10. إضافة طبقة الشبكة والـModels والRepositories وإدارة الحالة في Flutter.
11. ربط المقدمة والجلسة.
12. ربط الحول.
13. ربط الأصول والأسعار.
14. ربط الملخص.
15. عدم تعديل المساعد AI، إلا إذا ظهرت حاجة محددة لربطه بقاعدة البيانات ووافق عليها العميل.
16. تعديل الدفع فقط لربط سجلاته بالمستخدم والجلسة في قاعدة البيانات، دون أي خدمة خارجية.
17. إزالة القيم التشغيلية التجريبية من الشاشات الواقعة ضمن نطاق ربط البيانات، مع احترام استثناءي AI والدفع.
18. إضافة الاختبارات وتشغيل تدفق end-to-end.
19. توثيق التشغيل والإعداد وقرارات التصميم وحدود محاكاة الدفع.

لا تنفذ تغييرات ضخمة غير قابلة للمراجعة في دفعة واحدة. حافظ على Commits صغيرة ومحددة، ولا تعدّل ملفات لا تخص المهمة.

## 12. الاختبارات المطلوبة

### Backend

- تسجيل مستخدم وتخزين Argon2 hash بدلاً من كلمة المرور.
- رفض البريد المكرر وكلمات المرور غير المطابقة للسياسة.
- تسجيل الدخول الصحيح ورفض بيانات الدخول الخاطئة برسالة غير كاشفة.
- إصدار access/refresh tokens والتحقق منها وتجديدها وتدوير refresh token.
- إلغاء refresh token عند تسجيل الخروج ورفض الرموز الملغاة أو المنتهية.
- حماية المسارات وإرجاع المستخدم الحالي من `/api/auth/me`.
- إنشاء واسترجاع جلسة حساب.
- إضافة/قراءة/تعديل/حذف أصل.
- حساب الذهب والفضة والنقد والصناديق.
- حفظ واسترجاع الحول.
- صحة النصاب والإجماليات والتقريب.
- رفض القيم السالبة والعيارات غير المسموحة.
- منع مستخدم من قراءة أو تعديل بيانات مستخدم آخر.
- التعامل مع فشل خدمة الأسعار وبيان fallback.
- حفظ وقراءة سجل الدفع المحاكي مرتبطاً بالمستخدم والجلسة، دون اختبار أي مزود خارجي.
- بقاء البيانات بعد إعادة تشغيل الخادم.

### Flutter

- التسجيل وتسجيل الدخول واستعادة الجلسة وتسجيل الخروج.
- حفظ الرموز في `flutter_secure_storage` وتجديد access token بأمان.
- منع فتح الشاشات المحمية دون جلسة صالحة.
- parsing لجميع الاستجابات.
- loading/error/empty/data لكل شاشة متصلة.
- انقطاع الشبكة والمهلة وإعادة المحاولة.
- عدم فقد الأصول عند التنقل.
- تحديث الملخص بعد تعديل الأصول.
- استعادة الجلسة بعد إعادة تشغيل التطبيق.
- عرض سجل الدفع المحفوظ دون الادعاء بوجود تحقق من بوابة دفع خارجية.

### تدفق قبول كامل

1. يسجل المستخدم الدخول.
2. يوافق على الشروط وتُحفظ الموافقة.
3. تُنشأ جلسة حساب.
4. يحفظ بيانات الحول.
5. يضيف أصولاً وتُحفظ.
6. يغلق التطبيق ويفتحه وتظهر البيانات نفسها.
7. يظهر ملخص محسوب من Backend.
8. يبقى المساعد AI كما هو ولا يدخل في معيار قبول هذه المهمة.
9. تُحفظ عملية الدفع المحاكية في قاعدة البيانات وتُقرأ للمستخدم نفسه، دون اتصال خارجي.

## 13. معايير القبول النهائية

تعد المهمة مكتملة فقط عندما:

- لا توجد مبالغ أو أسعار أو تواريخ أو حالات أعمال ثابتة داخل الشاشات الواقعة ضمن نطاق ربط قاعدة البيانات؛ المساعد AI مستثنى صراحةً من هذا الشرط.
- كل شاشة مالية تقرأ Models قادمة من API.
- كل API مطلوب يحفظ أو يقرأ البيانات المناسبة من قاعدة البيانات، باستثناء الأسعار الخارجية وخدمة AI الحالية.
- لا يوجد `demo_user` في التدفق الفعلي.
- التسجيل والدخول والتجديد والخروج يعملون باستخدام FastAPI وSQLite دون Firebase أو Supabase Auth.
- كلمات المرور مجزأة باستخدام Argon2، والـrefresh tokens قابلة للإلغاء ومخزنة بصيغة hash.
- الجلسات والأصول والحول والحسابات وسجلات الدفع المحاكية مرتبطة بالمستخدم وتتحقق من الملكية.
- لم تتم إضافة أو تعديل أي خدمة دفع خارجية، ولم يتم تغيير AI إلا إذا كان هناك تكامل قاعدة بيانات معتمد.
- البيانات لا تضيع بعد إغلاق التطبيق أو إعادة تشغيل Backend.
- الملخص يطابق الأصول المخزنة وحساب Backend.
- الواجهة تعرض loading/error/empty بوضوح.
- لا توجد أسرار أو قاعدة بيانات محلية ملتزم بها في Git.
- تمر اختبارات Backend وFlutter المتفق عليها.
- README يشرح إعداد Flutter وPython والبيئة وتشغيل الخادمين والعناوين المطلوبة.

## 14. قرارات تحتاج موافقة العميل قبل إكمالها

- مصدر الرصيد/البيانات البنكية إن كانت شاشة التحليل ستبقى حقيقية.
- المرجع الشرعي النهائي لقواعد النصاب والحول وأنواع الأصول.
